ABSTRACT Modern software architectures heavily rely on APIs, yet face signiﬁcant security challenges,

particularly with Broken Object Level Authorization (BOLA) vulnerabilities, which remain the most critical
API security risk according to OWASP. This paper introduces Karate-BOLA-Guard, an innovative frame-

work leveraging Large Language Models (LLMs) and Retrieval-Augmented Generation (RAG) techniques

to automate security-focused test case generation for APIs. Our approach integrates vector databases for

context retrieval, multiple LLM models for test generation, and observability tools for process monitoring.
Initial experiments were carried out on three deliberately vulnerable APIs (VAmPI, Crapi, and OWASP Juice

Shop), with subsequent validation on ﬁfteen additional production APIs spanning diverse domains including

social media, version control systems, ﬁnancial services, and transportation services. Our evaluation metrics

show Llama 3 8B achieving consistent performance (Accuracy: 3.1-3.4, Interoperability: 3.7-4.3) with
an average processing time of 143.76 seconds on GPU. Performance analysis revealed signiﬁcant GPU

acceleration beneﬁts, with 20-25x improvement over CPU processing times. Smaller models demonstrated

efﬁcient processing, with Phi-3 Mini averaging 69.58 seconds and Mistral 72.14 seconds, while maintaining

acceptable accuracy scores. Token utilization patterns showed Llama 3 8B using an average of 36,591
tokens per session, compared to Mistral’s 25,225 and Phi-3 Mini’s 31,007. Our framework’s effectiveness

varied across APIs, with notably strong performance in complex platforms (Instagram: A=4.3, I=4.4)

while maintaining consistent functionality in simpler implementations (VAmPI: A=3.6, I=4.3). The iterative

reﬁnement process, evaluated through comprehensive metrics including Accuracy (A), Complexity (C), and
Interoperability (I), represents a signiﬁcant advancement in automated API security testing, offering an efﬁ-

cient, accurate, and adaptable approach to detecting BOLA vulnerabilities across diverse API architectures.

I. INTRODUCTION

Application Programming Interfaces (APIs) have become

the backbone of modern software architectures, facilitating

seamless communication between diverse systems. However,
this ubiquity also introduces signiﬁcant security risks, with

BOLA emerging as a critical vulnerability [1]. Traditional

security testing methods often struggle to keep pace with

the rapid evolution of APIs and the increasing sophistication

of cyber threats. As highlighted in [2], traditional security

testing methods often struggle to keep pace with the rapid

evolution of APIs and the increasing sophistication of cyber

threats, necessitating novel approaches that leverage machine
learning and artiﬁcial intelligence.

Recent research has demonstrated speciﬁc applications of

machine learning in API security testing:

•Anomaly Detection in API Trafﬁc: Machine learning

models, particularly Support Vector Machines (SVM),

have successfully identiﬁed abnormal API behavior pat-

terns [3]. These methods analyze features such as band-

width usage and request frequency to detect potential se-

curity breaches. However, the study exclusively employs
SVM with a linear kernel, which may not capture com-

Our framework addresses these speciﬁc limitations through:

•A modular architecture that allows for easy integration

of different LLMs and testing tools;

•RAG-enhanced test generation for improved context-

•An iterative, self-improving approach to test case gener-

ation and reﬁnement;

•Integrated observability tools for continuous monitoring

and improvement of test quality.

Our research is guided by the following questions:

•RQ 1 - To what extent does the integration of RAG

techniques enhance the quality and relevance of gen-

erated Karate DSL test cases for API security testing,

particularly focusing on BOLA vulnerabilities?

•RQ 2 - How does our RAG-enhanced approach impact
the coverage and speciﬁcity of generated test cases for

API endpoints potentially vulnerable to BOLA?

•RQ 3 - What are the trade-offs between test generation

time, accuracy, and comprehensiveness when employing

RAG techniques in API security testing?

Our approach directly addresses the gaps identiﬁed in

previous systematic reviews of API security testing method-

ologies. While Barabanov et al. [6] advanced systematic

approaches for BOLA vulnerability detection using Ope-

through analysis of real-world BOLA vulnerabilities, neither

fully addressed the automation challenges in security testing.

By combining LLMs with RAG techniques, our framework

speciﬁcally targets the limitations identiﬁed in [2], offering:

•Targeted security testing that goes beyond random ex-

ploration;

•Continuous learning and reﬁnement of test cases based

on execution results;

•Systematic approaches for identifying and testing poten-
tial BOLA vulnerabilities;

This systematic approach represents a signiﬁcant advance-

ment in automated API security testing, moving beyond the

current limitations of chance-based vulnerability discovery

toward targeted, intelligent test generation.

This section provides an overview of the current landscape in

API security testing, focusing on the critical nature of BOLA

vulnerabilities, traditional and emerging approaches to API

testing, and the growing role of LLMs in software testing. It

also introduces RAG techniques as a promising avenue for

enhancing LLM capabilities in API security testing.

A. BOLA VULNERABILITIES IN API SECURITY

Broken Object Level Authorization (BOLA) is recognized
as one of the most critical vulnerabilities in API security.

OWASP consistently ranks BOLA as the most severe API

security risk due to its prevalence and potential for exploita-

tion [1]. This vulnerability arises when APIs fail to enforce

proper authorization checks, allowing unauthorized access or

manipulation of resources.

The consequences of BOLA vulnerabilities include unau-

thorized data access, privilege escalation, and potential data
manipulation [8]. Addressing BOLA vulnerabilities is par-

ticularly challenging due to the complexity of modern API

architectures and the difﬁculty of implementing consistent

authorization mechanisms.

Emerging AI-driven approaches have shown promise in

tackling these challenges. For instance, Purple Llama Cyber-

SecEval [9] introduces a secure coding benchmark that aids in

B. CURRENT APPROACHES TO API SECURITY TESTING

Traditional API security testing methods, such as manual
penetration testing and automated scanning tools, face limita-

tions in addressing the evolving complexity of modern APIs

and advanced cyber threats [11]. These methods often lack

the scalability and adaptability required to identify context-

speciﬁc vulnerabilities like BOLA.

Recent advancements in API security testing aim to over-

come these limitations through innovative approaches, in-

cluding:

•Speciﬁcation-Based Testing: Generating test cases
based on API documentation to ensure adherence to

expected behavior [12];

•Machine Learning Techniques: Leveraging anomaly

detection algorithms to identify potential vulnerabili-

ties [8];

•Automated Test Case Generation: Frameworks like

RESTest employ diverse strategies to create comprehen-

sive test suites that improve coverage and accuracy [11];

•Adaptive Test Generation with LLMs: Approaches

like TestPilot, introduced by Schäfer et al. [13], utilize
LLMs to generate adaptive test cases, improving test

coverage and uncovering unique API vulnerabilities.

•Automated testing of REST APIs has seen signiﬁ-

cant advancements, with tools like AutoRestTest [14]

adopting innovative techniques such as Multi-Agent Re-

inforcement Learning (MARL) and Semantic Property

Dependency Graphs (SPDG) for dependency-aware test

generation. Our work, unlike AutoRestTest, which fo-

cuses on general fault detection, our framework pri-
oritizes security-speciﬁc weaknesses through a RAG

pipeline.

This distinction highlights the complementary nature of

our work. AutoRestTest demonstrates high generaliza-

tion for REST API fault detection, while our approach

narrows its focus to BOLA vulnerabilities, employing

iterative syntax validation and domain-speciﬁc test op-

timization.

While these advancements have enhanced the efﬁciency

and effectiveness of API security testing, they still fall short
in addressing the nuanced and context-speciﬁc nature of vul-

nerabilities like BOLA. There remains a pressing need for

methodologies that integrate adaptive, AI-driven frameworks

capable of providing comprehensive, scalable, and precise

security testing solutions.

C. LLMS IN SOFTWARE TESTING

The application of LLMs in software testing has gained sig-

niﬁcant traction in recent years. LLMs have demonstrated

effectiveness in various testing tasks, including test case
preparation, and automated test generation [15].

Key developments in this area include:

•The use of LLMs for generating unit tests, potentially

streamlining the software testing process [16];

•Application of LLMs in fuzzing techniques, addressing

the need for more automated and evolving vulnerability

detection methods [17];

•Exploration of LLMs as AI sparring partners for both

high-level task planning and low-level vulnerability

hunting in penetration testing scenarios [18];
•Generating security-centric assertions for hardware and

software systems, such as those outlined by Kande et al.

in Security Assertions by Large Language Models [19].

However, the use of LLMs in software testing is not without

challenges. Researchers have cautioned that LLMs should be

used carefully, as guidelines for their secure adoption are still

being developed [20].

D. RAG TECHNIQUES IN AI-ASSISTED TESTING

Retrieval-Augmented Generation (RAG) represents a promis-
ing approach to enhance the capabilities of LLMs in speciﬁc

domains. By combining the generative power of LLMs with

the ability to retrieve and incorporate relevant information

from a curated knowledge base, RAG techniques have the

potential to produce more accurate and context-aware out-

puts [21].

In the context of API security testing, RAG techniques

offer several potential beneﬁts:

•Improved relevance and speciﬁcity of generated test

cases;
•Enhanced ability to incorporate domain-speciﬁc knowl-

edge and best practices;

•Potential for generating more diverse and comprehen-

sive test scenarios, as demonstrated by Effective Test

Generation Using Pre-trained Large Language Models

and Mutation Testing [22].

Despite these promising aspects, applying RAG techniques

in API security testing, particularly for BOLA vulnerabilities,

remains largely unexplored. Recent advancements, such as
the ﬁndings in LLMSecEval: Evaluating the Security of LLM-

Generated Code [23], provide a foundational basis for lever-

aging LLM capabilities in test generation. Our work, how-

ever, aims to address this gap by developing and evaluating a

RAG-enhanced framework speciﬁcally designed for BOLA

vulnerability detection and mitigation.

H. LIMITATIONS AND BROADER QUALITY

CONSIDERATIONS

1) General Code Quality Metrics Not Included

While important for overall code quality, several traditional

software metrics have been intentionally excluded from our

framework:

1) Code Maintainability

•Readability and documentation quality;

•Code structure and organization;

•Comment completeness and clarity.

These aspects, while valuable, are general software

engineering concerns that apply to all code rather than
being speciﬁc to security test generation.

2) Cognitive Complexity

•Intellectual effort required to understand the test;

•Learning curve for new team members;

•Mental model complexity.

These factors are subjective and may vary based on

individual expertise and background.

3) Dependencies and Environmental Factors

•External library dependencies;

•Environment setup requirements;

•Cross-platform compatibility.

These considerations are more relevant to long-term
maintenance than to the immediate quality of generated

security tests.

I. RATIONALE FOR THE UNIFIED APPROACH

1) Focus on Generation: Each factor has been chosen

to reﬂect critical aspects of security testing. For ex-

ample, Interoperability emphasizes secure integration;

Complexity focuses on maintainability and operational

simplicity to mitigate risks of conﬁguration errors; and

Accuracy directly addresses the test’s ability to uncover

vulnerabilities.
2) Objectivity: The chosen metrics emphasize objectively

measurable aspects of test quality speciﬁc to BOLA

vulnerability detection.

3) Automation Compatibility: The selected metrics can

be evaluated programmatically, making them suitable

for automated assessment of generated tests.

4) Applicability to Generated Tests: In frameworks such

as Karate DSL, tests are often structured in a Given–

When–Then format. This inherent structure facilitates
the extraction and quantiﬁcation of the proposed factors

(e.g., the number of steps, the intricacy of request bod-

ies, and assertion logic), making the framework both

K. OVERVIEW OF KARATE-BOLA-GUARD FRAMEWORK

Karate-BOLA-Guard is designed as a modular, self-

improving framework that leverages LLMs and RAG tech-
niques to automate the creation and reﬁnement of API secu-

rity tests. The framework speciﬁcally targets BOLA vulnera-

bilities, generating test cases in Karate DSL format.

L. FRAMEWORK ARCHITECTURE

Figure 1 illustrates our framework’s architecture, where yel-

low components represent data storage and processing ele-

ments, while the blue-highlighted Karate Test Runner op-

erates in an isolated container. The framework processes

OpenAPI Speciﬁcations through several key stages: The OAS
Parser breaks down API speciﬁcations into manageable frag-

ments, storing them alongside BOLA and Karate DSL exam-

ples in the Vector Data Storage. The LLM Service interacts

with our RAG System to generate contextually-aware test

cases, which undergo syntax veriﬁcation before execution.

The Karate Test Runner executes these tests against con-

tainerized target applications, with results feeding into our

analysis pipeline. The Test Result Analyzer processes exe-
cution outcomes, generating reports that feed back into the

Vector Data Storage for continuous improvement. The LLM

Observability Service monitors the entire process, tracking

performance metrics and system behavior. This cyclic ﬂow

ensures continuous reﬁnement of test case generation and ex-

ecution, while maintaining component isolation for security

and scalability. Each component serves a speciﬁc purpose in

our security testing pipeline:

•OAS Parser: Decomposes API endpoint information
into manageable fragments.

•Vector Database: Stores API fragments and historical

test data for efﬁcient retrieval.

•RAG System: Queries the vector database for BOLA-

related vulnerability tests to augment the LLM’s context

for test generation.

•LLM: Generates initial Karate test scripts based on the

augmented context.

•Syntax and Compatibility Veriﬁer: Ensures generated

tests are syntactically correct and compatible with the

Karate framework.
•Karate Test Runner: Executes generated tests against

the target API in a containerized environment.

•Error Analysis: Analyzes test results and failures to

inform future test generation.

•Observability Tool: Monitors and logs the entire pro-

cess for analysis and improvement.

E. API SPECIFICATION PARSING

Recognizing the limitations imposed by constrained context

windows and the potential for extensive API speciﬁcations,

particularly in larger applications beyond microservices, we
developed a strategic approach to API speciﬁcation parsing.

This step is crucial for effective data management and pro-

cessing within our framework.

Our solution involves a custom-built OAS Parser com-

ponent, implemented as a Python script. This parser efﬁ-

ciently breaks down large API speciﬁcations into manageable

chunks, a common practice in data management for handling

substantial datasets. These parsed chunks are then system-

atically sent to our Vector Data Storage, implemented using
ChromaDB.

We’ve designed our storage system with scalability and

organization in mind. Each API’s parsed data is stored in

a separate collection within ChromaDB, with the collection

name corresponding to the speciﬁc API. This approach al-

lows our framework to handle multiple APIs concurrently,

storing their respective data in distinct collections within the

same ChromaDB instance. Such a design not only facilitates

efﬁcient data retrieval but also provides a clear structure for
managing and accessing API-speciﬁc information throughout

the test generation process.

This modular approach to data collection and preparation

ensures that our framework can adapt to various API sizes and

complexities, from small microservices to large-scale appli-

cations. It also sets the stage for future expansions, allowing

easy integration of additional APIs into our testing ecosystem

without necessitating signiﬁcant changes to the underlying

data management structure.
F. TEST CASE GENERATION PROCESS

With the knowledge base data in place and conﬁguration

details set in the conﬁg ﬁle for the RAG System, our test case

generation process can be initiated. The process follows these

steps for each API fragment:

6 https://github.com/karatelabs/karate

1) Initial Karate Test Generation: The system uses a

predeﬁned prompt to query the Vector Database for

BOLA-related API fragments. Combining these with

BOLA context examples and key elements from the
API Fragment (such as URI or other relevant data), the

LLM generates an initial test case. This test case is then

stored as a feature ﬁle in the designated output folder.

2) Karate Compatibility Veriﬁcation: The system takes

the generated feature ﬁle as context, along with addi-

tional context from the Vector Database. It then queries

the Karate DSL collection for relevant examples to

check for appropriate use cases. A specialized prompt

targets compatibility checking and test enhancements.
3) Karate Syntax Veriﬁcation: The output from the pre-

vious step serves as context, along with similar or

identical data retrieved from the Vector Database. This

time, the system uses a prompt speciﬁcally designed for

syntax validation.

4) Runner Step: The veriﬁed feature ﬁles are moved to a

separate directory, which is mounted as a volume in a

Docker container. This container includes the necessary

data to run the tests in an isolated environment against
the target service. The system generates both a raw

text report for processing and uploading to the Vector

Database, and an HTML report that can be automati-

cally opened in a browser for user inspection.

5) Error Check Loop: To address interoperability issues,

the system performs a predeﬁned number of error check

iterations (set to three in our experiments). When syn-

tax or other errors occur, the system makes a new call to

the LLM service. It retrieves error information for the
speciﬁc generated test case from the Vector Database

and uses this in a crafted prompt aimed at addressing

syntax errors and other relevant issues. The previous

step runs again, and if the error persists it runs throw

this error check loop.

6) Observability: Throughout this process, the system

makes calls to the Langfuse service, transmitting vari-

ous data such as token count, LLM name, input, output,

and any exceptions that occur. Users can access this
service via a web browser to observe the behavior of

the current run.

This systematic approach ensures a thorough and iterative

test case generation process, with built-in veriﬁcation steps

and error handling to maximize the quality and relevance of

the generated tests.

G. LIMITATIONS AND CHALLENGES

Despite the overall positive results of our experiments,

we identiﬁed several signiﬁcant limitations and challenges

that warrant discussion. While our framework demonstrated

promising test generation capabilities with BOLA oriented

vulnerability checks, certain constraints and areas for im-

provement emerged:

•Model Performance and Resources: The performance

gap between models suggests that larger, more resource-

intensive models may be necessary for optimal results.
Our speciﬁc conﬁguration choices (context window size

of 1000 tokens, temperature of 0.3) and hardware vari-

ations between CPU and GPU execution could signiﬁ-

cantly impact deployment in resource-constrained envi-

ronments and limit real-time applications.

•Vulnerability Coverage: While our approach improved

BOLA detection rates, it may not capture all possi-

ble vulnerability scenarios, particularly those requiring

complex, multi-step interactions. This limitation high-
lights the need for more sophisticated test generation

strategies. Additionally, our framework’s primary focus

on BOLA vulnerabilities might limit its effectiveness in

detecting other types of API security vulnerabilities.

•Model Dependencies: The variability in performance

across different LLMs indicates a dependency on the

speciﬁc model used, which may introduce inconsisten-

cies in test generation and affect the framework’s relia-

bility across different implementations.
•API Selection Bias: While we evaluated both inten-

tionally vulnerable APIs (VAmPI, CrAPI, OWASP Juice

Shop) and production APIs from APIRank, our results

may not generalize to all API types, particularly those

with unique authentication mechanisms or complex

business logic. Although effective on our test set, the

framework’s performance on diverse real-world APIs

with varying complexity requires further validation.

•False Positives: The potential for generating tests that
incorrectly identify non-existent vulnerabilities needs

further investigation and mitigation strategies to ensure

the accuracy and reliability of the generated test cases.

•Test Quality Assessment: Our evaluation metrics (Ac-

curacy, Interoperability, Complexity) might not capture

all relevant aspects of test case quality and effectiveness.

1) General Code Quality Metrics Not Included

While the following aspects are important for overall code
quality assessment, they have been deliberately excluded

from our primary evaluation framework:

1) Code Maintainability

•Readability and documentation quality;

•Code structure and organization;

•Comment completeness and clarity.

These aspects, while valuable, are general software

engineering concerns that apply to all code rather than

being speciﬁc to security test generation.

H. RATIONALE FOR EXCLUSION

Our decision to exclude these general code quality metrics is

based on several key considerations:

1) Focus on Generation: Our metrics prioritize aspects

directly related to the quality of automatically gen-

erated security tests rather than general code quality

concerns.

2) Objectivity: The chosen metrics emphasize objectively

measurable aspects of test quality speciﬁc to BOLA

vulnerability detection.

3) Automation Compatibility: The selected metrics can
be evaluated programmatically, making them suitable

for automated assessment of generated tests.

4) Domain Speciﬁcity: The framework focuses on secu-

rity testing characteristics rather than general software

engineering principles.

Despite these limitations, we have implemented several

strategies to strengthen the validity of our ﬁndings:

•Standardized Evaluation Environment: We main-

tained consistent conﬁgurations across all experiments,

including standardized token windows (1000 tokens)
and temperature settings (0.3), allowing for fair compar-

isons between models.

•Diverse API Testing: To address generalizability con-

cerns, we expanded our evaluation beyond vulnerable

test APIs to include production APIs spanning various

domains, including social media platforms, version con-

trol systems, and ﬁnancial services.

•Comprehensive Metrics: Our evaluation framework

employs multiple complementary metrics (Accuracy,

Interoperability, Complexity) to provide a holistic as-
sessment of test case quality, helping offset potential

limitations in individual metrics.

•Reproducibility Focus: We have made our implemen-

tation, including the complete dataset of generated tests

and analysis results, publicly available in our project

repository for transparency and reproducibility.

•Model Performance Documentation: We thoroughly

documented performance characteristics across both

CPU and GPU conﬁgurations, providing clear guidance
for deployment decisions in different resource environ-

ments.

While these strategies help mitigate our identiﬁed limita-

tions, we acknowledge that further research is needed to ad-

dress remaining challenges in automated API security testing.

RAG-enhanced testing solutions. The choice between faster

processing times and higher accuracy depends largely on

the speciﬁc use case and available computational resources.

These insights contribute valuable insight to the practical

implementation of RAG-enhanced API security testing, high-

lighting the importance of balanced resource allocation and

performance optimization in real-world deployments.

VI. FUTURE RESEARCH

Our ﬁndings point to several promising avenues for future
research in automated API security testing. The development

of dynamic model selection mechanisms presents an imme-

diate opportunity for advancement, potentially incorporating

real-time API characteristic analysis for optimal model de-

ployment. Resource optimization remains a critical area for

investigation, particularly in the context of large-scale API

testing environments.

The potential for cross-model learning mechanisms

presents an intriguing direction for future research, which
could enable the development of hybrid approaches that com-

bine the strengths of different model architectures. Advanced

RAG techniques, particularly in the realm of context-aware

embedding generation and adaptive similarity metrics, offer

promising opportunities for improving test generation accu-

racy and efﬁciency.

Furthermore, the development of sophisticated perfor-

mance prediction models could signiﬁcantly enhance the

practical utility of the framework. Such models could incor-
porate API complexity assessment and resource utilization

forecasting, enabling more efﬁcient resource allocation in

large-scale testing environments. These research directions,

grounded in our empirical ﬁndings, suggest a rich landscape

for future investigation in the ﬁeld of automated API security

testing.

In conclusion, Karate-BOLA-Guard represents a signiﬁ-

cant step forward in automated API security testing, partic-

ularly for BOLA vulnerabilities. Using the power of LLM
and RAG techniques, our framework offers a more efﬁcient,

accurate, and adaptable approach to identifying and miti-

gating critical API security risks. As APIs continue to play

a central role in modern software architectures, tools like

Karate-BOLA-Guard will be crucial in ensuring the security

and integrity of these vital components.
