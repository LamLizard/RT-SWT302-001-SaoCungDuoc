ABSTRACT

Mobile software development turns around quickly, which induces inadequate testing to meet this

short-lived pace of development and release process. The traditional testing procedures just do not fit
such a rapid mobile paradigm. This study sets out to exploit two straightforward techniques, namely

equivalence partitioning and control-limit techniques, based on software cost and quality. The first

technique divides input domain into proper partitions that suit the software functions and selects cost

representative data from each partition for testing. The second technique keeps the outcomes within

the limits to ensure acceptable output. The contributions of these techniques prove to be reliable
steppingstones for mobile software development without losing sight of the founding methodologies.

The study envisions that future work should incorporate well-established techniques for developers

to set up rapid test-and-run procedures, whereby quality mobile software can be developed from this

fast paced and short-lived cycle.

KEYWORDS

Equivalence Partitioning, Control-Limit, Software Testing, Mobile Software Development

INTRODUCTION
Traditional software development has been ongoing for decades and, in essence, has become a

well-established process over the years. The advent of mobile applications has brought about new

development paradigms that change the game entirely. Perhaps the key factor of this change is time.

The fact that most mobile apps are small, short-lived, and abandoned by users when new comparable

apps arrive makes it unsuitable to maintain them in the same fashion as the traditional software
counterparts. One area to look into is the testing stage of the development process. The work processes

performed by developers (during unit tests, integration tests, combined test-run during system tests,

user acceptance tests, and the remaining stress tests, regression tests, etc.), are all time-consuming

processes that can take months to complete before the software is released. This is one thing mobile

apps cannot embrace in their development process because this process may not exceed 6–9 months
from start to release. Hence, it is obvious that, to abide by the typical testing process, the procedures

must be adjusted and arranged to fit this time constraint.

In principle, the test method involves many manual procedures that are time-consuming. Many

traditional test procedures are straightforward to use yet may not be suitable in some test scenarios

and environments. For example, in the mobile environment, users are anonymous, which makes it

hard to set up proper coverage of input data partitions manually (let alone performing the analyses of

user acceptance tests, test efficiency, cost, etc.). Conversely, this may inevitably lengthen the mobile

development life cycle.

To reduce this development life cycle, this study focused on shortening the test-and-run process.
The unit, integration, and system tests were combined into one test-and-run step whose procedures

were governed by two well practiced techniques in traditional software testing: equivalence partitioning

and control-limit techniques. These two techniques were chosen because they are straightforward to

understand, apply, and verify since they can be observed, performed, and examined visually both by

the developers and users, making the agile team work smoothly.
The first technique arranges input data in groups whose members are said to be equivalent,

that is, each datum can represent the group. The number of groups, or partitions, confines the size

of input data sets to be used in each test step. Thus, exhaustive testing does not constitute an issue.

The second technique sets up an interval to keep test outputs within the predefined range, having

lower and upper bounds. This scope is known as the control limit, which is a well-known statistical
technique. Should any of the test outputs fall outside this predefined range, a procedural correction

is called for to rectify the corresponding software functions. In so doing, the development process

can be sped up considerably.

The above two techniques offer developers the flexibility of data selection and representation

within a defined operational range. They are simple and straightforward to implement based on
well-defined theoretical fundaments. It will be evident how the development progresses as the

proposed methodology unfolds.

RELATED WORK

Modernization has increasingly used software to operate all functions for some time. This software
runs on traditional systems such as the world wide web, which gradually switched to mobile devices

in the form of mobile apps. Their development life cycle runs from the annual scale in traditional

systems to months in mobile systems. The most important deciding factor of this development is the

time required to release the product. This constraint imposes not only the crunch on development

pressure but also on development quality and cost. The rush on releasing apps in shorter timeframe
creates faulty software products, which in turn increases the “faulty” cost. Tassey (2002) revealed

the estimates of the economic costs of faulty U.S. software that ranged in the tens of billions of U.S.

dollars per year, representing just under 1% of the nation’s gross domestic product.

At the core of these issues is the difficulty in defining and measuring software quality. Common

attributes include functionality, reliability, usability, efficiency, maintainability, and portability. These
quality metrics are largely subjective and do not support quantification that can be used to design

testing methods for software developers. Muccini et al. (2012) investigated the challenges and future

research directions of testing mobile applications. They found contextual and mobility issues to look

into, namely, performance, security, reliability, and energy. The concerns were fault detection, test

case (random) selection, and test artifacts.
Edwards (2004) presented one aspect of studies on software testing based on Bloom’s

taxonomy, pointing out five perceived roadblocks that plagued learners, from trial-and-error to

Dunietz et al. (1997) presented a comprehensive approach to functional testing that could be

Grønli et al. (2019) looked into how mobile devices, the Internet of Things, and wearable devices

could come together in one ecosystem. This would further complicate the types of inputs to the test

and run experiment of mobile software.

Amen et al. (2015) explained on automated and manual testing for mobile application. In absence

of input data description, the distinction between both testing techniques were unclear as to how inputs
were categorized, prioritized, and executed procedurally. Thus, we could envision that succinct and

clear input data description were vital to the development of test and run of mobile software.

Durelli et al. (2019) discussed in detail on automating software testing using ML to improve cost

overruns and poor quality. By categorizing study type and testing activity, a number of ML algorithms

could be employed to aid in automation such as test-case generation, refinement, and evaluation. At
any rate, they still advocated manual searches and selects ML tools based on supervised learning

artificial neural networks for decision making, refinement, and cost prediction. We thus exploited

the cost idea to enhance cost analysis of this study.

Godefroid et al. (2008) advocated automatic code driven test generation using a program analysis

technique. They elaborated both static and dynamic test generations to create a set of input values
that examined as many program statements as possible with the help of additional constraint solver

techniques. Both approaches proved to be valuable procedures for testing in this study. The types

of failure had to be recognized to make it work effectively since Itkonen et al.’s (2013) study on

exploratory testing showed how the types of knowledge, application, and recognition of failure by

testers using this technique could be used as an oracle. At any rate, the scope of the effort had to be
thorough and efficient (Kuhn et al., 2004) to maximize effectiveness.

From small development team size such as agile, Talby et al. (2006) suggested pair programming,

collective ownership, and coding standard practices to focus on continuous creation of user acceptance

tests, where everyone tested to maintain the product size at test size. As product scale becomes larger,

software test size must expand. One suggestion to migrate software testing to the cloud was studied by
Parveen and Tilley (2010), who offered resources such as virtualized hardware, storage, and software

services that aided in reducing the execution time of large test suites in a cost-effective manner. This

encompassed test case independence, operational environment, high-volume automated testing, and

so forth. Finally, as software specification changed, regression testing had to be adjusted accordingly
(Leung & White, 1989) for test plan and test cases on reusable, retestable, obsolete, new-structural,

and new-specification test cases.

These prior works served as the bases for devising the proposed methodology in this study. We

will explore its detail in the sections that follow.

EXPERIMENTS

The experiments were performed in two steps, namely, data collection and the test-and-run

process. The first step was carried out in two separate tracks: manual and automatic. The manual

track gathered test data sets from users and divided them into partitions manually. The automatic

track used the same data sets and ran them through the described partitioning procedure. After this
first step, equivalence partitions of the input test data sets were obtained. The second step ran both

manual and automatic tracks separately so as to compare their cost and average out-going quality

outcomes accordingly. Details are described:

Data Collection

The experiments were set up with the development of simple apps as the target problem since the

emphasis was on input and test data partitioning rather than the app itself. The set up was completed
with awareness of some programming tactics such as feedback from log files (Meier & Lepp, 2022)

that could improve programming solving time. Thus, all unwanted variations to control a uniform

development process were precluded such as odd data (unique values, extreme points, over/under

limit values), exceptions, rare cases, local min/max, and data normalization.

There were two experimental apps for this study and one real industrial app that was just completed
recently. The experimental apps were an average/standard deviation app, a max/min app, while the

real industrial app was a straightforward user input patch to add additional fields to a purchase order

for a local company (identity was withheld for confidentiality and anonymity purposes).

A set of input mobile data was collected from the users to be used by the experimental apps. The

fact that both of those apps were number-oriented, where mobile phone did not have a wide range
of numeric coverage for input data, we decided to opt for integers since they were straightforward to

handle. In so doing, we incorporated additional coverage of input data patterns (Sets 1–11) to ensure

that the proposed procedure would cover the work properly. Table 1 shows the representatives of

input data used for the experimental apps.

Test and Run

The described setup was designed and implemented on a PC-based client-server configuration, as

shown in Figure 2. The first point of entry was the user who would be taking input data to the GUI/UX

subsystem and distributing (AWS amplify) to downstream functions, which included micro-services

and data-repository subsystems. A gateway (Amazon API) and cloud storage (Amazon S3) were set
up to handle the communication channels. Minor supporting micro-services were also provided to

automate those administrative transactions such as email and notification (simple notification service—

SNS), web data access (Restful API), and automatic service invocation (AWS lambda trigger).

The third app was run on a local PC since it was text-based input that required correctness to

actual data. There were only two input text data partitions, namely, correct input and incorrect input
partitions. The former had to match verbatim, whereas the latter mainly contained typographic errors,

misspelled, and extraneous words.

The test process was designed as an incremental process to test each app. The inputs to each

app were broken down into test items (or partitions) to be tested one at a time using the proposed

procedure. Each item was set up according to the test cases, called test backlog. Each test backlog had

to go through test operations op1 to opk, which were transactions taken on the test cases, where op1

would encompass set 1, op2 would encompass set 2, and opk would encompass set 12, progressively.
The test outputs would then be approved by the tester as a working increment, which signified to be

completed for that test item. The next test item was retrieved and underwent the same process until

all the remaining test items were exercised. All test results of this app then became a test deliverable.

This process is depicted in Figure 3.

Testing the third app was different from the former two apps since its inputs were characters

text, while the incorrect partition was randomly made-up input text just for subsequent verification

and correction. All character inputs were read as ASCII (integer) code so as to ensure that they were

printable characters (94 characters) to be described in the next sub-section.

DISCUSSION

One of the important reasons for mobile software testing is continuity between the stages of
development. As Fitzgerald and Stol (2017) pointed out in their study, keeping the continuity among

the disconnects is imperative to be a roadmap for continuous software engineering. Since mobile

software development is agile (Flora et al., 2014), somewhat fast, and ad hoc under time constraints,

assembling all test results from many disconnects can make the apps less holistic and less in continuity

in comparison with the proposed incremental testing process.
In the introduction of equivalence partitioning and control-limit techniques advocated by the

proposed test-and-run procedure, it was intended to keep the test stages as simple, straightforward,

and automated as possible, whereby the mobile app development life cycle would be agile, less time

consuming, and suitable for this fast-paced development process.

Although we picked two experimental apps as the case studies for the proposed test-and-run
procedure, their simplicity did not preclude both techniques from successful implementation. The

third app proved to be a similar success story since input data pattern fit with equivalence partitioning,

while the control limits were natural language that was straightforward to handle.

It is worth noting that many software testing processes focus primarily on the technical aspects

of the development. The associated cost analysis is an accountable step imposing on this forerunning
test process to gauge its effectiveness and financial worth. Thus, they are seldom combined as an

integral step into process planning and analysis. The proposed methodology devised a procedure that

combined these two steps into one with the least complication involved. In addition, quality was also

taken into account in the proposed methodology by means of the control-limit technique of using a

simple measuring function. Hence, quality and cost could be attained at the same time.
A small point to note: This study proposed an average time efficient procedure to perform the

equivalence partitioning process with the help of the control-limit technique, along with cost function

analysis. Nevertheless, time measurements were not conducted since most mobile apps are proprietary,

which made it difficult to investigate procedurally.

THREATS TO VALIDITY

One of the logical arguments to raise is different input data types that cannot be combined using
the same analysis and explanation. In this study, the two experimental apps and the third real app took

integers and characters as their inputs, respectively. Thus, statistical measurements would undergo

different procedures, wherein the explanations should be treated accordingly. There were two reasons

to justify this cause. Firstly, we considered character input to be ASCII code, which meant that they
were integer values. Equivalence partitioning was a general technique that could handle this type of

data adequately. Since we used simple measurements, namely, control limit and average out-going

quality, to explain the experimental outcome, numerical computations could be carried out directly for

both input data types. Secondly, the theoretical setup was simple and straightforward without having

to incorporate any advanced mathematical analysis. In addition, the software process with properly
set up environment would also run different apps in the same environment. Since we targeted to make

it with the least complication in the first place, the set up worked out as we introduced a new and

simple technique to implement in mobile software environment. Anything out of ordinary would be

superfluous and was not taking into consideration.

CONCLUSION

This study embarked on the test-and-run aspects of mobile software development with one
important objective in mind: continuous software engineering with high quality and low cost. The

input test data manipulation process was investigated, since it is a time-consuming stage in traditional

software development, using equivalence partitioning and control-limit techniques. A procedure
to handle data partitioning in relation to the control limit was analyzed and created to arrive at a

suitable solution. The test results were measured based on average out-going quality and cost that

were compared with the traditional method from their benefits point of view. The results show that the

proposed method exhibits slightly better average out-going quality and lower cost than its traditional

counterparts. The test-and-run procedure also simplifies and eases the mobile development process
to some degree, in particular, for character type input. At any rate, the benefits may stack up to be

significant for development as the number and size of mobile apps grow.

Future work should focus on a number of issues relating to the input data coverage of this

test-and-run process—ranging from mobile programming languages, adaptation of apps, connectivity

to networks, and limited resources to issues of lesser importance such as user interface, look and feel
for different types of input data, and diversity of input data. Thus, future Internet of Thing works

having many input data types as mentioned by Grønli et al. (2019) can be carried out straightforwardly

based on these the proposed equivalence partitioning and control-limit techniques with minimal effort

to resort to software tool assistance or data conversion.
