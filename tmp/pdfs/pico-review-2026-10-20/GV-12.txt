           BEYOND FLAKY TEST DETECTION: USING THE MODEL
       CONTEXT PROTOCOL FOR INTELLIGENT TEST FAILURE
                                  DIAGNOSIS IN CI/CD

     Abstract
     The article presents TeamCity QA Intelligence, a system for automated root
cause diagnosis of test failures in continuous integration environments. Manual
identification of failure causes remains one of the most time-consuming activities
in CI/CD workflows, requiring engineers to cross-reference stack traces, commit
histories, build logs, and historical test results. Connecting to the TeamCity REST
API through 19 read-only tools built on the Model Context Protocol (MCP), the
system enables an AI reasoning layer to access structured CI data and produce a
root  cause  classification   for  each   failure.  Three  diagnostic  categories  are
supported:   code   change   with   commit-level   attribution,   test   flakiness,   and
infrastructure fault. A Cowork plugin with seven pre-configured commands covers
routine  diagnostic  scenarios.  The  system  has  been  in  daily  operation  on  a
production TeamCity instance for four months, executing 167 analysis sessions. In
documented investigations, diagnosis time decreased from hours or working days
of manual analysis to minutes, depending on failure complexity; classifications
verified during routine triage were consistently confirmed. QA tests, unit tests, and
integration  tests  are  processed  through  a  single  pipeline  without  per-type
configuration.  An  open-source  implementation  is  provided  for  independent
verification.

      Problem  statement.        Modern  software  development  relies  on  continuous
integration pipelines that execute automated test suites with every code change. As
projects grow in scale, the number of test executions per day reaches thousands or
tens of thousands, and a fraction of these executions inevitably produce failures.
CI servers are highly effective at recording which tests failed, what error messages
they  generated,  and  which  build  contained  the  failure.  Answering  a  different
question, specifically why a given test failed in a given build, falls outside the
operational scope of current CI platforms and remains a manual analytical task.
      Diagnosing  the  root  cause  of  a  test  failure  in  practice  involves  several
sequential steps that span multiple data sources. An engineer examines the stack
trace,  reviews  recent  code  changes  in  the  version  control  system,  checks  the
historical pass/fail behavior of the same test across previous builds, and inspects
the build agent environment for resource or connectivity anomalies. Each step
requires switching between a different interface, and the diagnostic value of each
step depends on the conclusions drawn from the preceding ones. In large teams
with  frequent  commits,  the  number  of  candidate  causes  per  failure  increases
proportionally,  extending  investigation  time  from  minutes  to  hours  or,  in
ambiguous cases, to days.
      A key difficulty in this process is that failures from fundamentally different
causes can produce similar observable symptoms. A test that fails due to a newly
introduced code defect may generate the same assertion error as a test that fails
intermittently due to timing sensitivity or resource contention on the CI runner.
Without access to contextual signals, such as commit scope, test execution history,
and  agent-level  metrics,  assembled  into  a  single  analytical  view,  an  engineer

cannot reliably distinguish between these categories. Current CI tooling addresses
parts of this problem in isolation: flaky test detection flags statistically unstable
tests, build comparison  views  highlight  configuration differences, and commit
linkage shows which changes entered a build. Integrating these partial signals into
a single diagnostic sequence has remained a manual responsibility, creating an
opportunity for protocol-level automation.
      Recent advances in two areas have made automated diagnostic classification
feasible.   Open   protocol   standards   for   AI-tool   integration   now   allow   AI
applications  to    query  external  systems  through  structured  interfaces  without
requiring  custom  connectors  for  each  data  source.  In  parallel,  large  language
models   have   demonstrated   the   capacity   to   synthesize   information   from
heterogeneous  technical  artifacts,  including  log  fragments,  code  diffs,  and
configuration records, when provided with organized context.
      The purpose of this article is to present TeamCity QA Intelligence, a system
that classifies test failure root causes in TeamCity CI environments through MCP-
based integration of CI data with AI reasoning, and to evaluate its diagnostic
utility and time efficiency over a four-month operational period.
      Scientific novelty of the work         consists in four contributions: applying the
Model Context Protocol to CI/CD diagnostic tasks, which has not been previously
reported in the literature; proposing a three-category classification model (code
change,  test  flakiness,  infrastructure  fault)  that  extends  binary  flaky/non-flaky
detection to multi-class root cause diagnosis; implementing automated commit-
level attribution that identifies the specific code change and its author responsible
for a regression; and demonstrating a test-type-independent diagnostic approach
that processes QA automation tests, developer unit tests, and integration tests
through a single classification pipeline.

flakiness  have  expanded  considerably  in  recent  years,  driven  by  the  growing

recognition  that  non-deterministic  test  failures  undermine  the  reliability  of  CI

      Rasheed et al. [1, p. 12] conducted a multivocal review covering 651 sources
(560  academic  and  91  grey  literature),  identifying  concurrency,  test  order
dependency, and network availability as the most frequently documented causes of
non-deterministic test behavior. Static detection methods based on code pattern
analysis  and  dynamic  methods  based  on  repeated  test  execution  were  both
catalogued, and the authors noted that dynamic rerun-based approaches dominate
in industrial practice. One finding of particular relevance to the present study is
that  detection tools  identify which  tests are  flaky but  do  not provide  failure-
instance-level explanations, leaving engineers to determine the specific cause of
each occurrence manually.
      Parry et al. [2, p. 478] challenged the widely held assumption that flaky test
failures are isolated events. Analyzing 810 flaky tests across 24 Java projects over
10,000 test suite runs, they discovered that 75 percent of flaky tests belong to co-
occurring clusters averaging 13.5 tests per cluster. Manual inspection of stack
traces within these clusters revealed intermittent networking issues and external
dependency   instabilities   as   the   predominant   shared   causes.   A   practical
consequence of this clustering is that identifying the root cause for one test in a
cluster effectively resolves the diagnosis for all remaining tests in the same group,
which  strengthens  the  case  for  automated  classification  systems  capable  of
processing failures at the category level.
      Ahmad [5] developed MDFlaker, a tool that applies four factors (traceback
coverage, test smells, flakiness frequency, and test size) to a K-Nearest Neighbors
classifier for determining whether a failed test execution is flaky. Integrated with
GitHub  and  Travis  CI,  MDFlaker  operates  in  real-time  during  CI  runs  and
represents one of the few tools that attempt root cause analysis beyond simple
pass/fail counting. Its classification target is binary (flaky or not flaky), however,

      Silva et al. [6, p. 3108] investigated the relationship between computational
resources and test flakiness across 52 projects. Their experiments showed that
restricting CPU and memory on CI runners increased failure rates for tests that
passed reliably under normal resource conditions. Error messages produced by
resource-constrained failures were structurally similar to those from genuine code
defects, meaning that stack trace analysis alone could not differentiate between the
two causes. Agent-level metadata such as CPU utilization and memory availability
at execution time was identified as a necessary signal for accurate classification.
Combined with the findings of Parry et al. [2], this result indicates that effective
diagnosis must draw on data sources beyond the test result itself, including build
agent properties and cross-build execution history.
      Lam et al. [11, p. 206] reported on the methodology used at Microsoft to
identify root causes of flaky tests in an industrial codebase of over 10 million
lines.  Their  approach  correlated  test  failure          occurrences  with  code  change
timelines to determine whether a failure was induced by a recent modification or
by an independent factor. High accuracy was achieved for code-change attribution,
but the method required substantial infrastructure (dedicated analysis pipelines,
historical  data  warehouses)  and  focused  exclusively  on  the  binary  distinction
between   code-induced   and   non-code-induced   failures   without   further   sub-
classification of  the  non-code category.  For organizations without comparable
infrastructure,   a   lighter-weight   approach   that   achieves   similar   attribution
granularity would address a practical accessibility gap.
      Durieux et al. [12, p. 256] studied 3,551,558 builds on Travis CI and found
that approximately 18 percent of builds were restarted manually by developers.

      A separate line of development relevant to this study is the Model Context
Protocol (MCP), which provides the technical infrastructure for connecting AI
reasoning to external data sources through standardized tool interfaces. Hou et al.
[3]  provided  the  first  systematic  academic  analysis  of  MCP,  mapping  its
architecture, lifecycle phases (creation, deployment, operation, maintenance), and
associated  security  risks  across  four  attacker  types.  Their  threat  taxonomy
documented vulnerabilities including tool poisoning, preference manipulation, and
credential theft. For CI-related applications, their analysis establishes that MCP
servers accessing build and test data must enforce read-only access patterns to
prevent unauthorized modifications, a constraint that directly informed the read-
only design of the system described in this article.
      Singh et al. [8] surveyed MCP adoption across sectors including healthcare,
financial  services,  and  developer  tooling.  Productivity   metrics   from  early
enterprise   adopters   showed   that   MCP-enabled   agents   reduced   integration
development time by approximately 50 percent compared to custom connector
approaches. Developer tooling emerged as the most active adoption domain, with
over 10,000 public MCP servers registered by early 2026, yet the survey did not
identify any MCP server designed specifically for QA diagnostic workflows in CI
environments.
      Hughes  [9]  proposed  an  enterprise-grade  security  framework  for  MCP
deployments,   incorporating   OAuth   2.1   authorization,   zero-trust   network
principles, and input validation mechanisms. Applied to CI environments, these
recommendations  address  the  risk           of  exposing  sensitive  test  data  or  build
configurations  through  improperly  secured  MCP  endpoints.  For  a  diagnostic
system that queries production CI instances, the authentication and authorization
patterns described by Hughes represent necessary deployment prerequisites.
      Ehtesham et al. [10] analyzed the economic impact of MCP standardization,
reporting measurable gains in deployment speed and maintenance cost reduction

      Published MCP server implementations for CI systems such as TeamCity,
Jenkins,  and  GitHub      Actions  provide  generic  capabilities:  reading  build  logs,
triggering builds, and retrieving project metadata. None of these implementations
incorporate  failure  classification  logic  specific  to  QA  workflows,  such  as
distinguishing  code  regressions  from  flaky  behavior  or  attributing  failures  to
infrastructure  conditions  based  on  error  signatures.  Commercial  CI  analytics
platforms offer proprietary AI-driven failure analysis, but they operate as external
SaaS  dependencies  outside  the  MCP  ecosystem  and  do  not  publish  their
classification methodologies for independent evaluation. An open-source system
that  combines  MCP-based  CI  data  access  with  three-category  root  cause
classification (code change, test flakiness, infrastructure fault) and commit-level
attribution has not been described in the reviewed literature.
      Materials  and  methods.        System  architecture.      TeamCity  QA  Intelligence
operates as an MCP server exposing 19 read-only tools to any MCP-compatible AI
client. Each tool wraps one or more TeamCity REST API endpoints and returns
structured  data  optimized  for  diagnostic  reasoning.  Five  functional  groups
organize the tools by the type of CI context they provide. Build metadata tools
retrieve build status, timestamps, trigger information, and the identity of the build
agent that executed the run. Test result tools extract individual test outcomes,
failure messages, stack traces, and execution durations from a specified build.
Change  attribution  tools  return  the  list  of  commits  associated  with  a  build,

including   modified   file  paths,  change  descriptions,  and  author   identifiers.
Historical comparison tools query           previous builds  for the same configuration,
returning pass/fail sequences for a given test over a configurable time window.
Aggregation and comparison tools cluster failed tests by shared cause, compute
differentials between two builds, and assemble a consolidated analysis context for
a failed build alongside its most recent green build.
      When a diagnostic session begins, the AI reasoning layer issues a sequence of
tool calls determined by the failure context. For a single test failure, the typical
sequence    retrieves  the  build  details,  extracts  the  failing  test  record,  pulls  the
commit list for that build, and queries the same test across the 10 most recent
builds of the same configuration. For a build-wide failure summary, all failing
tests are extracted first, and the subsequent tool calls are batched across the full
set. A schematic representation of this data flow, from the TeamCity API through

      Three-category classification. Each failure is assigned to exactly one of three
categories based on convergent signals from the tool outputs. Assignment follows
a  decision  sequence:  code  change  is             evaluated  first,  then  flakiness,  then
infrastructure.
      Code-change attribution requires three concurrent conditions: the test was
passing  consistently  in  recent  builds  of  the  same  configuration,  at  least  one
commit entered the build between the last passing and first failing execution, and
the files modified in that commit overlap with the package or module exercised by
the failing test. When all three conditions are met, the system records the commit
hash, the author, and the modified file list as evidence.
      When no commit satisfies those attribution criteria, the system evaluates the
test's  historical  behavior  for  flakiness  indicators.  A  non-monotonic  pass/fail
pattern across a window of 10 builds, with no corresponding code modifications
between state transitions, triggers a flakiness classification. A secondary signal

reinforces this category: if the same test passes on a rerun within the same build,
the non-deterministic nature of the failure is confirmed independently of historical
data.
      Infrastructure faults represent the residual category, applied after code and
flakiness attributions have been ruled out. Signals specific to this category include
the simultaneous failure of multiple unrelated tests within the same build, and
error messages referencing timeouts, connection refusals, or memory-allocation
failures. When such signals are present, the system records the identity of the build
agent that executed the run and the error indicator that correlated with the failure.
Live agent resource metrics (CPU and memory utilisation) are not exposed by the
TeamCity REST API and are therefore not used; classification relies on error
signatures and co-failure patterns observable through the API.
      Access interfaces. Two access paths are available. For exploratory analysis,
an engineer or AI client can invoke any combination of the server's 19 read-only
MCP tools directly, constructing custom diagnostic sequences suited to unusual
failure  patterns.  For  routine  daily  use,  a  Cowork  plugin  provides  seven  pre-
configured  commands  that  chain  multiple  tool  calls  into  single  invocations.
Analyze-failed-build accepts a build identifier, retrieves all relevant context, and
returns a classified diagnosis with supporting evidence. Build-comparison-report
takes two build identifiers and produces a differential report highlighting tests that
changed status between them. Recent-builds-summary processes recent builds of a
target and returns a grouped classification of failures across the three root-cause
categories. Flaky-test-review examines a build configuration over a window of
recent builds and identifies recurring and intermittent failure signatures. Change-
impact-review correlates the commits included in a build with the failures they
may have introduced. Test-count-stability tracks fluctuations in the number of
executed tests across builds, surfacing tests that silently disappear from the run.
Generate-report   produces   a   self-contained   HTML   document   consolidating

      System scope. Input granularity ranges from a single build configuration to a
list of configurations or an entire TeamCity project. When multiple configurations
are analyzed, results are aggregated to surface cross-configuration patterns. If the
same agent appears as an infrastructure-fault source across several configurations,
the aggregated view flags it as a systemic environmental issue requiring attention
from DevOps. Every test result is treated identically regardless of its origin: for the
classification pipeline, a test is a record with a name, a status, a duration, and
optional failure details. Whether the record was generated by a QA automation
framework, a developer unit test suite, or a deployment verification script does not
alter the diagnostic logic, which means that QA engineers, backend developers,
and DevOps teams can use the same system without separate configurations or
adapters.

      Cross-build comparison through the system established that suite coverage
was in fact identical across all runs. The cause lay in test naming: a parameterized
test generated multiple argument sets, some of which embedded live data values
(entity counts) into the displayed test name. Whenever different argument sets
happened to produce identical display names, TeamCity collapsed them into a
single reported entry. JUnit executed all 49 parameterized runs in every build,
while  TeamCity  reported  between  45  and  48  depending  on  how  many  name
collisions the current data produced. The apparent instability was thus a pure
reporting  artifact,  amplified  by  the  naming  design  of  the  tests  themselves.
Reconciling  executed-versus-reported  test  counts  across  builds,  logs,  and  the
parameterization source manually is estimated at two to three working days; with
the system, the equivalent investigation takes an estimated 20 to 40 minutes.
      A second case illustrates the infrastructure category. A database-test build
had failed on every scheduled run for a week. Investigation through the system
traced the failure to the build environment: the TeamCity agent had been upgraded
to JDK 21, while the project's Gradle 7.6 cannot read Java 21 class files, so the
build failed during init-script execution before any test had               started. The failure
stage and the absence of relevant code changes ruled out both code-change and
flakiness attributions. The fix was confined to upgrading the Gradle wrapper to
8.8; neither product nor test code was modified. A typical manual investigation of
such a failure takes two to five hours; with the system, the end-to-end diagnosis
took approximately one hour (measured).

to the true origin. Invoked through a single command, the system collected every
failed test with its stack trace from the affected build and from several preceding

availability within a single MCP-integrated tool. Each of the compared approaches
addresses a subset of these capabilities, but none provides all of them in a unified
workflow accessible through a standardized protocol.

      Compared to the industrial methodology reported by Lam et al. [11, p. 208],
the  MCP-based  approach  achieves  commit-level  attribution  without  requiring
dedicated analysis pipelines or historical data warehouses. Where the Microsoft
approach  depended  on  custom  infrastructure  proportional  to  the  scale  of  the
codebase, the present system operates on standard TeamCity REST API endpoints
available in any TeamCity installation. Durieux et al. [12, p. 258] documented that
18  percent  of  Travis  CI  builds  were  restarted  by  developers  who  could  not
determine failure causes from the CI interface. Automated classification at the
point of failure provides an immediate category              assignment that can inform the
restart decision: a code-change classification signals that a rerun will reproduce
the  failure,  while  an  infrastructure  classification  suggests  that  a  rerun  on  a
different agent may succeed.
      The architecture is positioned to         scale beyond individual use. Because the
diagnostic logic is encapsulated in a standard MCP server, a remote deployment
using the Streamable HTTP transport could serve multiple engineers from a single
instance, and classification results could be surfaced team-wide through TeamCity
report   tabs,   removing   the   need   for   each   engineer   to   invoke   commands
independently. Targeted  feedback to the  author of an  implicated commit  is a
natural  extension:  TeamCity  already  provides  built-in  commit-author  failure
notifications, and the present system could refine them by triggering only on code-
change classifications, suppressing the flaky and infrastructure noise that generic
notifications include. These team-scale capabilities are identified as future work
and were not part of the validated single-user configuration.
      Several constraints limit the scope of the reported findings. Evaluation was
conducted  on  a  single  TeamCity  instance  within  one  organization  over  four
months. Classification performance may vary across organizations with different
CI   configurations,   test   suite   sizes,   commit   frequencies,   or   agent   fleet
compositions. Infrastructure fault detection depends on error signatures and co-

      Conclusions.       Automated  root  cause  classification  of  test  failures  through
MCP-based CI data integration proved operationally viable over a sustained four                            -
month evaluation period. In documented investigations, diagnosis time decreased
from  hours  or  working  days  to  minu           tes  depending  on  failure  complexity,  and
classifications   verified   during   routine   triage   were   consistently   confirmed.
Structuring  19  read     -only  tools  into  functional  groups  aligned  with  diagnostic
reasoning steps allowed an AI layer to assemble the same evid                        ence an engineer
would gather manually, but across all relevant data sources simultaneously and in
a fraction of the time.
      A  three   -category  model  (code  change,  test  flakiness,  infrastructure  fault)
captured  the  failure  types  most frequently  encountered  in                 daily  CI  operations.
Commit-level  attribution  within  the  code            -change  category  provided  actionable
specificity: identifying the responsible commit and its author directed corrective
effort   to   a   concrete   target.   Classification   boundaries   between   categories,
particularly between infrastructure faults and flakiness, represent the primary area
where diagnostic precision can be improved through richer environmental signals.

      Standardizing the diagnostic interface through MCP eliminated the need for
custom connectors between the AI reasoning component and the CI data source.
Adapting the system to other CI platforms such as Jenkins, GitHub Actions, or
GitLab  CI  would  require  replacing  the  TeamCity-specific  API  wrapper  layer
within each of the 19 tools, while the classification logic, the decision sequence,
the Cowork command structure, and the reporting format remain unchanged. Any
MCP-compatible client can use the tool set without modification, and the open-
source  implementation  allows  organizations  to  adapt             the  classification  logic,
extend the tool set, or contribute refined heuristics. Cross-platform portability and
community-driven  development  represent  practical  next  steps  toward  broader
adoption.
