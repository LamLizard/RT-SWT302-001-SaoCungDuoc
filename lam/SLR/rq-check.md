# Kiểm chứng RQ — phần của Dương Vĩ Lâm

**Nguồn phụ trách:** ACM Digital Library (+ đọc thêm 7 bài theo phân công: hàng #10–#16 của bảng gộp)

**RQ:** Trên 45 yêu cầu của RESTestBench^P, phân hoạch tương đương kết hợp phân tích giá trị biên^I, so với sinh dữ liệu ngẫu nhiên đồng đều cùng ngân sách^C, khác nhau thế nào về số mutant riêng biệt bị phát hiện theo từng dạng yêu cầu^O, khi một mutant chỉ được tính nếu test vượt qua bản gốc nhưng thất bại trên mutant theo oracle của benchmark?

**PICO:** P = 45 yêu cầu RESTestBench (15/dịch vụ) · I = EP + BVA · C = random đồng đều, cùng request budget, 10 lần chạy/seed cố định · O = số mutant riêng biệt, phân tầng theo dạng yêu cầu; mutant chỉ tính khi test pass bản gốc và fail trên mutant theo oracle requirements-based.

**Kết luận phần của tôi: KHÔNG có phản chứng.** 0/8 bài giống ≥3/4; cả 8 bài 0/4. Gần nhất:
- **I:** R021 dùng **robust BVA đơn lẻ** (§4.4, tr.6); K101 dùng boundary constants 0/1/−1 + combinatorial — chưa bài nào dùng **EP + BVA kết hợp** trên tham số request.
- **C:** K66/K167/K101 so công cụ cùng ngân sách **thời gian/số lần chạy**, không phải **uniform random cùng request budget**.
- **P/O:** không bài nào dùng RESTestBench; không bài nào đếm **mutant riêng biệt**.

**Nhãn tính mới (thẻ RQ):** Đối chiếu bảng 8 bài trên: **không bài nào giống ≥3/4 → nhãn = `new`**.

**Xác minh lần 2 trên toàn văn PDF (18/10/2026):** đã rà lại 8/8 PDF, không đổi nhãn — (i) **0/8** lần xuất hiện chuỗi “RESTestBench”; (ii) **0/8** bài dùng **EP+BVA** làm can thiệp chính (R021 chỉ robust BVA; K101 chỉ boundary constants 0/1/−1 + combinatorial; K52 — ngoài 8 bài — dùng EP/BVA để test chính công cụ IDLReasoner); (iii) **0/8** có nhánh **uniform random cùng request budget** (K66/K167/K101 chỉ so công cụ với cùng thời gian/số lần chạy); (iv) **0/8** đếm **source mutant/mutation score** — các từ “mutation” ở K167/K101/K07/K21 là **request mutation/fuzzing**, không phải mutation testing. Kết luận 0/4 cho cả 8 bài là đúng.

## 2. Lớp tìm kiếm bổ sung + rà nghiên cứu mới nhất

- **Truy vấn:** Semantic Scholar Graph API — `query=REST API mutation testing`, `year=2025-2026`, fields `title,year,venue,externalIds,citationCount`, ngày chạy **2026-10-18** → **12 kết quả**; kiểm tra chéo venue/năm/citation bằng OpenAlex theo DOI (cùng ngày). Chọn theo thứ tự: cùng bài toán/metric → venue/benchmark lớn → mới nhất.
- **Đã chọn 3 bài mạnh nhất 12 tháng:**
  1. **LlamaRestTest: Effective REST API Testing with Small Language Models** — FSE 2025 (Proc. ACM Softw. Eng.), DOI `10.1145/3715737`, 42 citation (S2). 12 real-world services; so RESTGPT, RESTler, MoRest, EvoMaster, ARAT-RL. **Chưa đo:** không so EP+BVA với uniform random; không dùng RESTestBench; metric coverage/bug, không phải số mutant riêng biệt.
  2. **RESTestBench: A Benchmark for Evaluating the Effectiveness of LLM-Generated REST API Test Cases from NL Requirements** — EASE 2026, arXiv `2604.25862`. 3 dịch vụ, 106 yêu cầu/228 mutation (Table 3; repo ghi 103 yêu cầu); định nghĩa **requirements-based mutation metric**. **Chưa đo:** chỉ đánh giá LLM (non-refinement vs refinement), không so EP+BVA với random, không phân tầng kết quả theo dạng yêu cầu cho EP/BVA.
  3. **MioHint: LLM-Assisted Request Mutation for Whitebox REST API Testing** — ICSE 2026, DOI `10.1145/3744916.3773228`. **Whitebox**, LLM hỗ trợ mutation; không phải black-box, không dùng RESTestBench, không có nhánh uniform-random cùng request budget.
- **Kết luận:** 3 bài mạnh nhất 12 tháng **không lấp RQ**; RQ vẫn đo được điều các bài chưa đo: (i) so EP+BVA với uniform random **cùng request budget**, (ii) **số mutant riêng biệt theo từng dạng yêu cầu**, (iii) trên **45 yêu cầu RESTestBench**. Không có phản chứng mới.

## 3. Ghi chú khả thi từ các paper tôi đọc

- **RESTestBench:** repo `github.com/casablancahotelsoftware/RESTestBench` — 3 dịch vụ chạy Docker, requirements + mutant, license AGPL-3.0. **Cỡ dữ liệu lệch cần chốt:** paper Table 3 ghi **106 yêu cầu/228 mutation** (FastAPI 63/141 · TodoApp 14/22 · RealWorld 29/65), repo ghi **103 yêu cầu**; RQ dùng **45 yêu cầu (15/dịch vụ)** → phải chốt **quy tắc chọn 15/dịch vụ** (theo ID/thứ tự hoặc phân tầng) và ghi vào proposal §5 trước khi chạy.
- **Chi phí ước tính:** 45 yêu cầu × 2 kỹ thuật × 10 lần chạy = **900 lượt**; mỗi yêu cầu ~2,15 mutation (228/106) → 45 yêu cầu ≈ **97 mutant** cần chạy qua 2 nhánh. Chạy local Docker nên khả thi trong 1–2 ngày; cần **seed cố định + request budget cố định**.
- **Auth/rate-limit:** các bài dùng API công khai (K66, K101) gặp auth/rate-limit và phải tạo nhiều account; RESTestBench chạy local nên **tránh được rào cản này** — lợi thế cho RQ.
- **Code:** R021 **không có code công khai**; K66 (RestCT), K101 (EmRest), K37 (replication package) có artifact; nhóm không cần code của họ — chỉ cần RESTestBench + script EP/BVA tự viết.
- **Bài học từ hạn chế:** spec/ground truth thủ công là rủi ro lặp lại (K66, K101, P12/K55, K46); nhiều bài chỉ 1–20 SUT (K52 3 API, K66 11 API, K46 4 SUT, K02 1 ứng dụng); metric xấp xỉ (coverage/TCL) không thay được mutant (K07); chỉ bắt 5XX là quá hẹp (K21) → dùng **mutation oracle của RESTestBench** là hợp lý.
